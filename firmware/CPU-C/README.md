# CPU-C - galvo and fiber laser

CPU-C of the Control Board V2 drives the galvanometer scan head over the
**XY2-100** protocol and controls the Raycus RFL-C200A fiber laser. It is the
RP2350B with the 8 MB PSRAM populated, which is intended to buffer the scan
trajectories.

The XY2-100 signalling is generated by the RP2350 **PIO** block rather than in
software, so the bit clock stays jitter free while the CPU prepares the next
position.

## Pin map

Verified against the CPU-C sheet of the V2 schematic:

| Signal | GPIO | Goes to |
| --- | --- | --- |
| `PIO_15V_RLY` | GP19 | relay K7, −15 V to the scan head |
| `PIO_PWR_RLY` | GP20 | relay K6, +15 V to the scan head |
| `PIOXDATA` | GP33 | AM26LS31 → `XCH±` on the DB15 |
| `PIOYDATA` | GP34 | AM26LS31 → `YCH±` |
| `PIOCLOCK` | GP35 | AM26LS31 → `CLK±` |
| `PIOSYNC` | GP36 | AM26LS31 → `SYNC±` |

The head is unpowered until firmware closes K6 and K7, so nothing moves until
GP19 and GP20 are driven high.

### xy2_100.pio

Two state machine programs:

| Program | State machine | Role |
| --- | --- | --- |
| `xy2_100` | SM0 | master - drives the X data line and generates CLOCK |
| `xy2_slave` | SM1 | slave - drives the Y data line and generates SYNC |

Both shift out a 20 bit frame, one bit per clock, with `side_set` carrying the
CLOCK and SYNC lines so the levels change in the same cycle as the data. The
frame is reloaded with a non-blocking `pull`, so when the FIFO is empty the
previous position is repeated instead of stalling the scan head.

### galvo_test_with_relays.cpp

Frame format is `[C2 C1 C0 | DATA(16) | PARITY]` with even parity over the 19
leading bits, shifted left by 12 so the 20 bit word sits at the top of a 32 bit
FIFO entry. Positions are mapped from millimetres onto the full 16 bit range,
with a per-axis inversion flag.

Because GP33-GP36 are above pin 31, the code uses **PIO2** with its GPIO window
moved to the upper bank:

```c
PIO pio = pio2;
pio->gpiobase = 0x10;   // PIO2 now addresses GP16..GP47
```

A PIO instance can only reach 32 of the 48 pins on an RP2350B. Writing
`gpiobase` directly works because `pio_get_gpio_base()` reads the register back
from hardware, so the SDK's internal pin translation picks it up; the idiomatic
call is `pio_set_gpio_base(pio, 16)`.

Both state machines are stopped, their FIFOs cleared, preloaded with one frame
each and then restarted together, so the X and Y frames stay aligned.

## Building

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Produces `build/galvo_test.uf2`. Copy it to the CPU-C USB-C port in BOOTSEL
mode.

## Status

*Bring-up.* `galvo_test_with_relays.cpp` is test code from the hardware bring-up
and is not the final firmware:

- the shape is hard coded (rectangle or circle, selected by a `#define`) and
  precomputed into a fixed 20 000 point buffer
- there is no command interface, so the host cannot send a scan path yet
- the 8 MB PSRAM is not used
- there is no fiber laser control in this project
- `PICO_BOARD` is `weact_studio_rp2350b_core`, a development board rather than
  this PCB; the pin map above is correct but the board definition is not
- it contains a leftover debug pin, `pio_gpio_init(pio, 6)`. GP6 is outside
  PIO2's GP16-GP47 window, so that call cannot do what it looks like and should
  be removed or moved into the window

The intended firmware is a custom port of
[OpenGalvo](https://github.com/Dev-Fernandez/OpenGalvo), originally written for
the Teensy 4.0.

See **[../../pcb](../../pcb)** for the schematic.
