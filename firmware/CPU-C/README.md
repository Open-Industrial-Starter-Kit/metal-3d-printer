# CPU-C - galvo and fiber laser

CPU-C of the Control Board V2 drives the galvanometer scan head over the
**XY2-100** protocol and controls the Raycus RFL-C200A fiber laser. It is the
RP2350B with the 8 MB PSRAM populated, which is intended to buffer the scan
trajectories.

The XY2-100 signalling is generated by the RP2350 **PIO** block rather than in
software, so the bit clock stays jitter free while the CPU prepares the next
position.

## Pin map

Verified against the CPU-C sheet of the V2 schematic:

| Signal | GPIO | Goes to |
| --- | --- | --- |
| `PIO_15V_RLY` | GP19 | relay K7, −15 V to the scan head |
| `PIO_PWR_RLY` | GP20 | relay K6, +15 V to the scan head |
| `PIOXDATA` | GP33 | AM26LS31 → `XCH±` on the DB15 |
| `PIOYDATA` | GP34 | AM26LS31 → `YCH±` |
| `PIOCLOCK` | GP35 | AM26LS31 → `CLK±` |
| `PIOSYNC` | GP36 | AM26LS31 → `SYNC±` |

The head is unpowered until firmware closes K6 and K7, so nothing moves until
GP19 and GP20 are driven high.

### xy2_100.pio

Two state machine programs:

| Program | State machine | Role |
| --- | --- | --- |
| `xy2_100` | SM0 | master - drives the X data line and generates CLOCK |
| `xy2_slave` | SM1 | slave - drives the Y data line and generates SYNC |

Both shift out a 20 bit frame, one bit per clock, with `side_set` carrying the
CLOCK and SYNC lines so the levels change in the same cycle as the data. The
frame is reloaded with a non-blocking `pull`, so when the FIFO is empty the
previous position is repeated instead of stalling the scan head.

### galvo_test_with_relays.cpp

Frame format is `[C2 C1 C0 | DATA(16) | PARITY]` with even parity over the 19
leading bits, shifted left by 12 so the 20 bit word sits at the top of a 32 bit
FIFO entry. Positions are mapped from millimetres onto the full 16 bit range,
with a per-axis inversion flag.

Because GP33-GP36 are above pin 31, the code uses **PIO2** with its GPIO window
moved to the upper bank:

```c
PIO pio = pio2;
pio->gpiobase = 0x10;   // PIO2 now addresses GP16..GP47
```

A PIO instance can only reach 32 of the 48 pins on an RP2350B. Writing
`gpiobase` directly works because `pio_get_gpio_base()` reads the register back
from hardware, so the SDK's internal pin translation picks it up; the idiomatic
call is `pio_set_gpio_base(pio, 16)`.

Both state machines are stopped, their FIFOs cleared, preloaded with one frame
each and then restarted together, so the X and Y frames stay aligned.


## JSON control API

CPU-C speaks the same JSON envelope CPU-B already uses with the host, so one client talks to
both processors the same way. Lines are newline terminated; every reply is a single line.

### Transports

| Transport | Use |
| --- | --- |
| CPU-C's own USB CDC port | direct, for bring-up and debugging |
| UART link from CPU-B | normal path, with the host talking only to CPU-B |

A reply always goes back on whichever transport the command arrived on, and carries
`"from":"cpuc"` so a host reading CPU-B's mirrored stream can tell the two processors apart.
On boot CPU-C emits `{"from":"cpuc","event":"linkUp"}` on the CPU-B link.

### Reaching CPU-C through CPU-B

Add `"target":"cpuc"` and CPU-B forwards the line verbatim over the UART without parsing it:

```json
{"target":"cpuc","type":"serialPing"}
```

`"target":"cpub"`, or no `target` at all, is handled by CPU-B itself. Any other value gets
`{"result":"failure","error":"unknownTarget"}` from CPU-B.

Forwarding is deliberately dumb: CPU-B passes the raw text through and needs no knowledge of
CPU-C's command set, so the two can be extended independently.

### Envelope

```json
{"type":"<serialPing|get|set|command>", ...}
```

`type` selects the family; `get`/`set`/`command` each need a second key naming the operation.

### Commands

| Request | Reply (after `"from":"cpuc"`) |
| --- | --- |
| `{"type":"serialPing"}` | `"result":"success"` |
| `{"type":"get","getType":"getFirmwareVersion"}` | `"firmwareVersion":"0.1.0-bringup"` |
| `{"type":"get","getType":"getStatus"}` | `firmwareVersion`, `galvoStreaming`, `galvoPower`, `laserInterlock`, `laserMainPower`, `laserRemoteOn`, `shape`, `numPoints`, `uptimeMs` |
| `{"type":"get","getType":"getDebuggingSettings"}` | `debuggingBase`, `enableJsonResponse` |
| `{"type":"set","setType":"setDebuggingBase","value":true}` | `"result":"success"` |
| `{"type":"set","setType":"setEnableJsonResponse","value":true}` | `"result":"success"` |
| `{"type":"command","commandType":"setGalvoPower","value":true}` | `"result":"success"` |
| `{"type":"command","commandType":"setGalvoStreaming","value":false}` | `"result":"success"` |
| `{"type":"command","commandType":"setLaserInterlock","value":true}` | `"result":"success"` |
| `{"type":"command","commandType":"setLaserMainPower","value":true}` | `"result":"success"` |
| `{"type":"command","commandType":"setLaserRemoteOn","value":true}` | `"result":"success"` |

`setGalvoStreaming` stops CPU-C pushing new XY2-100 frames without stopping the state
machines, so the head holds its last position rather than the scan restarting.

### Relays

CPU-C drives five relays. Each command takes `"value"` as a boolean; `getStatus` reports the
current state of all of them.

| Command | GPIO | Net | Switches |
| --- | --- | --- | --- |
| `setGalvoPower` | GP20 + GP19 | `PIO_PWR_RLY`, `PIO_15V_RLY` | K6 and K7, the +15 V and −15 V rails to the scan head |
| `setLaserInterlock` | GP24 | `Interlock_RLY` | the RFL-C200A interlock pin pairs on the DB25 |
| `setLaserMainPower` | GP26 | `LaserPowerON` | `REMOTE_PWRON`, the laser's main-power emulation |
| `setLaserRemoteOn` | GP25 | `LaserRemoteON` | `REMOTE_ON`, the laser's start emulation |

**Every relay is open at boot** and only closes when something asks, so powering the board
energises nothing.

`setGalvoPower` deliberately drives **both** K6 and K7 from one command. They are separate
nets on the board, but the scan head needs a symmetric supply and energising +15 V without
−15 V would feed it an asymmetric one, so the API does not expose the rails individually.

The three laser commands are **individual relay controls, not a power-up sequencer.** The
Raycus RFL-C200A has a required order — interlock closed first, then main power, then remote
on, with timing between them documented in the vendor guide and embedded in sheet 6 of the
schematic. Honouring that order is the caller's job; CPU-C will close any of these relays on
request, in any order. A sequencer with the interlock and timing enforced belongs in the
firmware before the laser is ever fired in anger.

### Errors

`{"result":"failure","error":"<code>"}` with one of:

| Code | Meaning |
| --- | --- |
| `unknownJsonType` | `type` missing or not recognised |
| `unknownJsonGetType` / `unknownJsonSetType` / `unknownJsonCommandType` | second key not recognised |
| `missingJsonKey` | a required key, usually `value`, was absent |
| `lineTooLong` | the line exceeded 512 characters |
| `unknownTarget` | from **CPU-B**, when `target` is neither `cpub` nor `cpuc` |

`serialPing` answers even when `enableJsonResponse` is false, so it stays usable as a
liveness check in any configuration. Everything else goes quiet.

### Parser limits

The parser is deliberately small and has no dependencies. It handles a **flat** object of
string, boolean and number values: no nesting, no arrays, no escape sequences, and a 512
character line limit. That is enough for control traffic. Bulk scan data is expected to get
its own binary framing rather than being forced through this.

Booleans accept `true`/`false` and also `1`/`0`, which several clients emit.

### Trying it

With CPU-C on USB, or through CPU-B by adding `"target":"cpuc"`:

```json
{"type":"serialPing"}
{"type":"get","getType":"getStatus"}
{"type":"set","setType":"setDebuggingBase","value":true}
```

Per-sweep console logging is off by default, so replies are readable; turn it back on with
`setDebuggingBase` when you want it.

## Building

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Produces `build/galvo_test.uf2`. Copy it to the CPU-C USB-C port in BOOTSEL
mode.

## Status

*Bring-up.* `galvo_test_with_relays.cpp` is test code from the hardware bring-up
and is not the final firmware:

- the shape is still hard coded (rectangle or circle, selected by a `#define`) and
  precomputed into a fixed 20 000 point buffer
- there is a control API but no scan path interface, so the host still cannot send geometry
- the 8 MB PSRAM is not used
- the fiber laser's relays can be switched, but there is no power-up sequencer, no
  PWM/analog power control and no reading of the laser's status inputs yet
- `PICO_BOARD` is `weact_studio_rp2350b_core`, a development board rather than
  this PCB; the pin map above is correct but the board definition is not
- it contains a leftover debug pin, `pio_gpio_init(pio, 6)`. GP6 is outside
  PIO2's GP16-GP47 window, so that call cannot do what it looks like and should
  be removed or moved into the window

The intended firmware is a custom port of
[OpenGalvo](https://github.com/Dev-Fernandez/OpenGalvo), originally written for
the Teensy 4.0.

See **[../../pcb](../../pcb)** for the schematic.
